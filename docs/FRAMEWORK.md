# How This Framework Works

This is a framework for engineering projects run by a team of AI agents under the oversight of a single human. It's meant to be adopted across a range of projects, so everything here describes how the organization operates, independent of what it's building. A project lives entirely inside a **repository**: a shared folder whose version-control software permanently records every change, its author, and its explanation. A **commit** is one such saved change; commits are shared by **pushing** them to a common server, and finished work **merges** into the main line — the official, agreed version of the project — only after passing every check. The founding principle: AI agents forget everything between sessions and can't be relied on to remember or self-report accurately, so **everything (roles, rules, work, decisions, evidence) exists as files in the repository**, and the most important rules are enforced by scripts that mechanically refuse a rule-breaking commit, rather than by trust.

## The rules and their enforcement

- **The constitution** is one shared rules file every agent must read before acting. Most of it is the framework's standard template — how work moves, how reasoning is preserved, how enforcement works — with the project's specifics filled in: how the roles map onto its roster of seats, which files each seat may edit, and the escalation thresholds (say, how far over schedule a phase may run before the human hears about it). The founding agent — the future orchestrator — writes it, which means it wrote the very rules that bind it and granted its own permissions. So before real work begins, the human **ratifies** it: reviews the rules, the seats, and their permissions, and formally accepts them — the one legitimizing act the organization can't perform on itself.
- **Two enforcers.** A **commit script** checks every rule before a change can be saved and refuses violations outright. **Continuous integration (CI)** — an automatic checker on the shared server — then re-runs every rule across the project's entire history, so even if an agent skips the script on its own machine, the violation is caught before the work can merge.
- **One agent per commit, with its journal entry.** Every commit carries one agent's work — so every change has exactly one answerable author — *plus* a new entry in that agent's **journal**: an append-only diary recording what triggered the work, what the agent read, its reasoning, what it did, and the evidence for its claims. Entries only accumulate; mistakes are corrected by later entries, never by editing old ones, because a record that can be tidied isn't evidence.
- **Write scopes.** Each seat may only edit the set of files its charter (next section) declares for it — keys that open some rooms and not others. The commit script refuses anything outside them.
- **Rules change by procedure, not by edit.** Amending the constitution takes a **decision record** (described in The Paper Trail below) accepted by a role other than its proposer. If the change alters enforcement, the **enforcement self-test** must be updated too: a suite that deliberately constructs a rule-breaking commit for each rule and proves the script still refuses it. Finally, a role the new rule will constrain **countersigns** the change — checking that the enforcement matches the stated rule, no wider and no narrower — and may legitimately refuse to sign.

## Who does what

Every role — a **seat** — is defined by a **charter**: a versioned document stating the seat's identity and write scope, its mission and duties, how it works with each other seat, what "done" means, how it's evaluated, its journal obligations, when it must send a problem upward, and the sources it works from. It's called a seat because the role outlives any agent filling it: agents are started ("spawned") for a session and then gone; the seat, its charter, and its journal persist. Reading its own charter is every agent's first act after spawning. And because every duty is written down, mismatches are visible: if a seat starts doing work its charter doesn't assign it — most dangerously, taking over a check on its own work — a reviewer can compare what happened against the charter and call it out.

- **Sponsor** (the one human). Sets the project's scope and technical vision: the organization can't know what to build until the human irons that out with it — chiefly through the specification lead, who turns the vision into written requirements. Beyond that, the sponsor owns only a short, fixed list of decisions: ratifying the constitution, approving the escalation rules, a one-time setup of the server's protections (the settings that stop anyone from rewriting the project's history), and final approval of any lesson the project exports for others to reuse. Design choices, work routing, and review verdicts are explicitly *not* theirs; a single status file tells them when something needs their attention.
- **Orchestrator.** The only agent that may spawn other agents, and the only one that commits. Other seats edit files and hand the result over; the orchestrator commits each seat's work under that seat's name, plans, routes tasks, and escalates to the sponsor. It is a router and clerk with total file access — so the one thing it must never do is write the substance itself: the work, evidence, and verdicts it moves are always authored by other seats.
- **Specification lead.** Turns the sponsor's vision into the specifications and the numbered requirements (numbered so a test can point at exactly what it verifies), and owns the decision records and documentation. Nothing is built that it hasn't specified; nothing merges undescribed. When the other leads disagree about where their work meets, it settles the dispute — always in writing, never informally.
- **Implementation lead.** Turns the specifications into the thing itself — it owns everything that ships as the product. It breaks the specified work into task packets; the actual building is mostly done by workers, spawned one packet at a time, and the lead reviews each worker's returned work — bouncing what falls short, accepting what meets the spec — before that work can continue toward merge. It never writes the tests that will grade its own output; those belong to the verification lead.
- **Verification lead.** Owns the tests, the reference models (independent models of what correct behavior looks like), and the measurements, and issues the pass/fail verdicts ("sign-offs," below) that every merge requires. It derives its tests from the specification, never from the implementation — checking what was promised, not what was built.
- **Workers.** Short-lived agents spawned for exactly one task, given only that task's context, returning exactly what it asks, then discarded. Their output is always reviewed by their lead.
- **Auditor.** Audits every seat, including the orchestrator that spawns it — partly by re-running the commands other seats recorded as evidence, to check the results actually come out as claimed. It may write only its own reports, so it cannot fix what it finds — deliberately, because an auditor that repairs things has an incentive to find only what it can repair. Its critical findings reach the sponsor unedited.

## The paper trail

Work and verdicts travel between seats as **packets** — versioned files with an ID, an author, an addressee, and a status — never as messages that vanish.

- **Work orders** — task packets with a lifecycle: issued → returned → accepted, or bounced back by the reviewing seat with a numbered defect list. The bounce history is preserved, never tidied away.
- **Decision records** — created whenever the project faces a non-obvious choice: picking between two design approaches, changing a rule, redefining what a measurement means. Each captures the decision, the alternatives considered, and why each lost — so a rejected idea can't return as fresh six months later. One seat proposes; a different seat accepts.
- **Findings** — defect reports graded critical, major, minor, or note. Any seat may file one, even against itself; a finding closes only when repaired, or ruled on with written grounds by whoever owns the thing it's about — never by being ignored.
- **Gates and sign-offs** — a **gate** is a committed checklist that must be fully signed before the project advances a stage; each signature points to an entry in the signing seat's own journal saying it signs. A **sign-off** is the verification lead's verdict on one finished piece of work, with the exact commands to reproduce it. Failing verdicts stay on the record beside their fixes.
- **Seeded-defect campaigns** — to prove the tests actually catch things, the auditor secretly plants known bugs in an isolated copy of the work, never the real product. Before any of those bugs exist, the verification lead writes down and freezes ("seals") its predictions — which kinds of planted bug its tests will catch, and which they'll miss. Results are scored against that frozen record, so success can't be redefined afterward. A passing test suite isn't trusted — it's tested.
- **Roster and program state** — one file lists every seat with links to its charter and journal; another holds the live picture: the current milestone (the named unit of planned work), open tasks, gate status, and pending escalations. A brand-new agent can reconstruct where everything stands from files alone.

## Working habits

Before touching anything, an agent checks that the workspace matches what its instructions said to expect, and stops with a report if it doesn't — proceeding would mean building on something that silently changed. Refusing a task, with its reasons recorded, is a legitimate and respected outcome. Seats don't converse directly: the orchestrator carries messages between them word-for-word, with any additions of its own explicitly marked. Work is pushed at every stopping point, because work that exists only inside one session dies with it. When a session crashes mid-task, its partial work is preserved as evidence outside the workspace but removed from it, and the replacement agent starts over from the committed record — a half-finished edit can't be safely resumed, because its author can't be asked what it was about to do. A fixed **escalation ladder** — defined classes of problem, from a routine blocker to a critical audit finding, each with its route upward — decides what reaches the human.

## Keeping itself honest

The system assumes its own rules will decay and be overstated, so it audits itself:

- **Honesty grades.** Every rule in the constitution states how it is *actually* enforced: **machine-checked** (a script refuses violations), **review-enforced** (a habit a seat keeps — no script involved), **performed once** (it happened once, on a date — not a standing practice), or **planned** (not built yet). The grade tells a reader exactly how much weight a rule can bear: a machine-checked rule holds under pressure, while a review-enforced one holds only as long as someone keeps the habit. Anyone adopting the framework can see precisely which protections come guaranteed and which they must build or watch themselves — because a habit mistaken for a guarantee is how rules quietly die.
- **Tested, not self-reported.** The grades aren't taken on faith. The auditor tests them by actually attempting whatever each rule claims to block, then watching whether the block happens — and any grade that turns out to be overstated gets corrected.
- **Residues.** Every rule also names its **residue** — the part its enforcement can't reach — and assigns a seat to watch that gap. Example: "only the orchestrator commits" is a habit no script verifies, so it is labeled as such and someone is on the hook for watching it.
- **The failure museum and the lessons harvest.** Expensive mistakes are rewritten as general lessons that would hold in any project, not just the one that learned them — the failure museum. Before any gate closes, each seat must reread its own journal and mine it for new lessons — the harvest — and "found nothing" must be said explicitly, never skipped.
- **Built to be copied.** The framework is designed so another team can adopt it whole, and it ships as two halves because both are needed: a **handbook** pairing every rule with the failure it exists to prevent — a rule whose purpose you can't state is a rule you'll drop exactly when it matters — and a **runnable toolkit** containing the actual enforcement scripts, so adopters don't rebuild the machinery from scratch. Whether it truly transfers isn't assumed; it's measured: the package is handed to outsiders who have never seen it, they set a project up from scratch, and every place they stall or improvise is logged and fixed in the next revision.
