# BILL — Adoption audit of docs/PROCESS.md (sixth edition)

Seat: independent adoption reviewer. Question: could someone with nothing in common with this program stand up a new organization from this document plus its named shell? Method: full read of the core (4,920 lines) and the memoir's Part 0/Annexes; re-execution of the document's own printed checks; inspection of the real enforcement surfaces (scripts/, agents/PROTOCOL.md, .github/workflows/, .claude/agents/); live probe of the shell repository; cross-check of run-2's halt log against the sixth edition's repairs. Findings are ranked by adoption risk and tagged with Sal's criterion; where a finding is mine rather than the framework's probe, I say so.

**Calibration first, so the findings below are weighted correctly.** The apparatus works as printed: the sentinel grep returns 0 against the core; the printed awk command reproduces exactly 71 headings; both halt logs, the round-4 verdict, and the posture list exist at their cited paths; and — my own probe, beyond the framework — `git ls-remote` against `github.com/renatom11/generic-agentic-fpga-org` succeeds and returns `main = 2ad82c3`, byte-identical to §6.0's pin ("Shell observed at: main = 2ad82c3, on 2026-08-11"). The shell is real, public, and currently unchanged since the pin. Every finding below is against a document whose self-checks pass.

## FINDINGS, ranked by adoption risk

### F1 — The only path a real adopter will take is governed by a document this one has never audited, and the document says to prefer it. [C5.2/C5.8 — MAJOR, disclosed (capped from CRITICAL); CONFIRMED]
Anchor: §6.0, the precedence rule (~line 4204). Quote: "With the shell in hand, the shell's own `BOOTSTRAP.md` governs the sequence. ... It is not this document's order and it does not agree with it." And: "the with-shell path is untested: both executed adoption runs happened in worlds that could not reach the shell, so the only path this unit has evidence for is the one no adopter with network access will take."
Probe: shell reachability confirmed live (see calibration). So a real adopter WILL have the shell, WILL be routed to BOOTSTRAP.md, and the document's two committed halt logs — its entire replicability evidence — measure the path that adopter will not walk. The precedence rule names exactly one known disagreement (platform-protection timing) and resolves it; the number of unnamed disagreements is unknown by construction, and the doc–shell drift check "does not exist" (stated in the opening paragraph). Day one therefore begins with dual-document execution: follow an unaudited order while cross-reading this document's grounds, with one adjudicated conflict and no instrument for the rest.
Expected: at minimum, the core should convert §6.2 into the *invariant checkpoints any order must hit* (founding range declared; machinery before adversarial review; CI green before protection; live-fire bounce; gate closes before WO-0001) so an adopter running BOOTSTRAP.md can check conformance without re-deriving which §6.2 warnings are order-specific and which are structural. It half-does this ("read §6.2's grounds for each step") but never separates invariant from sequence. The disclosure is exemplary; the exposure is still the largest in the unit.

### F2 — The first act of adoption (act 1a: "decide the seats") is underdetermined, and the document knows it from its own halt log and did not repair it. [C5.9/C1.2 — MAJOR, undisclosed in the core; CONFIRMED]

### F3 — The spawn/launcher/session layer is a substrate assumption quarantined nowhere, and the launcher artifact is unresolvable from the export unit. [C9.2, plus my own reading — MAJOR; CONFIRMED]
Anchor: §6.0 kit table: "The launcher prompts | The spawn-time text ... | this repository, launcher directory."
Probe: grep for the actual path. The launchers live in `.claude/agents/` — named only in the constitution (agents/PROTOCOL.md §2: "via the launcher definitions in `.claude/agents/`"), a platform-specific hidden directory. Neither the core, nor the memoir's name map (Annex C.1 says only "launcher directory", with no path; C.2's artifact table has no launcher row) resolves it. So the kit row's "where its original lives" pointer dangles for a reader of the two volumes — the only unresolvable row in the table.
The deeper gap is mine to flag: Annex A covers the spawn *constraint* (A.1) and the capability *tiers* (A.8), but nothing covers the spawn *mechanism* — what a session is, how a launcher binds seat to prompt to tier, what runtime feature "spawning" even is. §1.0 calls the orchestrator "a single long-running session" and no annex row says what that assumes. An adopter on any other agent framework (or a partly-human team) must invent the entire session-management layer, and unlike every other invention in the record, this one is not named as a step, a parameter, or a halt. Related and unstated: **who executes §6.2** — both tested runs used a blank AI as executor, the prose addresses human engineers, and no sentence says whether the §6.2 executor is, becomes, or spawns the orchestrator that act 1b onboards.
Expected: an Annex A row ("how seats are instantiated: measure your runtime's session/spawn primitives; the launcher is the artifact that binds them"), a resolvable kit pointer, and one sentence in §6.2 naming its executor.

### F5 — The core exceeds its own substrate's single-read limit, and its only fine-grained navigation aid has no anchors. [C4.5/C4.3 — MAJOR; CONFIRMED by measurement]

Annex A.3 anchors the one-readable-unit rule at 262,144 bytes ("the largest file the agents' own reading tool will return in one call — 256 KiB in this environment") and §2.2 states the failure class: "a file that exceeds what a reader (human or agent) can load in one piece stops being read at all." The core is 20% past its own soft threshold in the very runtime it was built in — the declared blank-AI executor of §6.2 cannot load the document in one call there. The document applies this discipline to journals and never to itself, and unlike the journals there is no rotation story. Compounding it: the 71-entry subsection index is plain text (the awk derivation cannot emit links), so an agent or human "jumping by reference" past the seven Contents entries must scan. The split's fragment-safety property (no superseded law in any fragment) is real and verified — but fragment-reading is not merely possible here, it is *forced*, and the doc never says so about itself.
Expected: the boundary block or A.3 should state the core's own byte count against the A.3 anchor and say what a windowed reader should load first. (The memoir at 157,785 bytes is fine.)

## What day one actually looks like, and where the document leaves the adopter stranded
Step −1 is a real repair — sponsor recruited first, platform inspected, CI runnable, shell fetched — and the sponsor's five-item surface plus docs/SPONSOR.md make the human side genuinely executable. Then, in order, the stalls: minute one, the precedence fork routes you onto an unaudited order (F1); hour one, act 1a asks you to decide a seat set the document refuses to bound (F2), while nothing tells you who is executing these steps or what a "session" is on your runtime (F3); day one to two, eight charter bodies must be rewritten from nine headings with the load-bearing mechanisms enumerated for only one seat (F4); throughout, Step 0's trace runs through the history volume (F6), and if your reader or platform differs from the origin's, A.3 and Step 2 hand you the same improvisations run two logged (F7). Everything after Step 3 is well-determined: the self-test, the live-fire bounce, the founding declaration, the solo-adopter honesty block, and the DoD are the strongest adoption prose in the document.
